1.What an "ACH exposure limit violation" actually is

In plain terms, so the rest makes sense.

ACH is the network US banks use to move money in bulk — payroll, supplier payments, tax payments. A company hands its bank a file containing many payments, and the bank pushes them through the ACH network on the company's behalf.

When the bank processes that file, there's a gap between sending/collecting the money and it actually settling. During that gap the bank is on the hook if the company can't cover it. That risk is called exposure. To cap the risk, the bank gives each company an exposure limit — a ceiling on how much it will process before funds settle. There are two flavours: credit exposure (money going out on the company's behalf) and debit exposure (money being pulled in that could later bounce). Typical ceilings in this use case: credit ≈ $300k, debit ≈ $200k.

When a company's total activity for the day goes over its limit, that's an exposure limit violation — an "exception." The bank's core system (FIS) automatically holds the file (the payments do not go out) and flags it for a human to review. Every exception has to be worked and cleared the same day (hard 8 PM cutoff; a 60-minute underwriter SLA).

Working an exception means deciding, per held item: is the company good for it or not? Approve → release the payments despite the overage. Reject → purge (return/cancel) the transactions. Making that call needs a few facts: how far over the limit it is (the overage), whether it's credit or debit, the company's balance/standing, and sign-off from an RBO underwriter.

Today this is done by hand — consolidating spreadsheets, logging into ACHPS, capturing balance screenshots, emailing the underwriter, filling purge forms. UC-02 automates it: Pega runs the case, Amendia (AI agents) does the judgement work, and humans stay in the loop to approve the steps that actually move money.

2.How Pega orchestrates the whole thing

The macro process. Pega owns the case end-to-end and calls Amendia three times; we don't need a new BPMN for this — the flow in words:

  1. FIS holds the file and emails an "exposure exceeded" spreadsheet to the bank's ops inbox.
  2. Pega's email bot ingests it, creates a Case (one per company per batch — this case's id is our case_id), extracts the details, and computes the overage.
  3. Pega checks whether the limit is really breached (allowing for any temporary limit increase). If not, it's handled/closed. If yes, Pega gathers the supporting facts from the systems (ACHPS transaction type, the company's PCG relationship contact, balance) — with human help — and updates the case.
  4. → Pega triggers Amendia Segment A to assess the exposure and recommend a disposition. Amendia returns a recommendation + rationale + a drafted underwriting message.
  5. Pega drafts the email from Amendia's message; a human reviews and sends it to the RBO underwriter + PCG, then waits for the underwriter's decision (60-min SLA).
  6. → When the decision returns, Pega triggers Amendia Segment B to enforce that decision and orchestrate execution — prepare a release or a purge instruction. Amendia returns the instruction.
  7. Pega updates its records / fills the purge form + logs the FIS ticket (human review as needed); FIS removes the hold and releases, or the purge is processed.
  8. → Pega triggers Amendia Segment C to close out — confirm the disposition applied, mark the case complete, purge working data. Amendia returns done.
  9. Pega closes the case and emits a process-completed message.

Where the cohort lives in all this

Every trigger Pega sends in steps 4, 6, 8 carries the same case_id. Each spawns an ordinary Amendia process instance — and because all three share that value, they join one cohort. The step-9 process-completed message (also carrying case_id) is the cohort close. Amendia never sequences these — Pega does; Amendia just observes its three segments as one case.

4.What this sets up for the build

Once you're happy with the shapes above, the two build steps become concrete:

① Stub MCP server — ach-exposure-stub

One MCP server exposing the 10 tools the three segments bind (following the existing wire-stan / rest-stan stub pattern). Each returns plausible canned ACH data:

Seg A: classify_exposureget_client_risk_profilerecommend_dispositiondraft_underwriting_message

Seg B: capture_decisionprepare_releaserequest_purge

Seg C: verify_dispositionmark_completedpurge_working_data  +  a notify_pega send-message tool each segment uses to hand its result back.

② Pega orchestrator stub — a small web app

  • Sends the three triggers (AssessExposureRequested, EnforceDecisionRequested, CloseoutRequested), each stamped with the same case_id — driving Amendia's normal trigger front door.
  • Listens for each segment's handback (the notify_pega message) and advances to the next trigger — standing in for Pega's case orchestration and the human/underwriter waits.
  • Emits the final process-completed message (carrying case_id) — the registered cohort close that disposes the cohort instance.
  • A tiny UI: enter a case_id + a scenario (credit/approve, debit/reject), then "Run case" to fire the sequence — so we can watch the cohort open, accumulate its 3 members, and drain to closed.
