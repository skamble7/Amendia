Declaring a Cohort

How to describe a cross-system process to Amendia so it can watch your segments, warn you before a deadline slips, and tell you who was late — without ever taking control of the process.

◆ The one idea to hold onto

A cohort is an observer, not a controller. You are not building a workflow that Amendia runs — you are writing down what you expect a larger process (spread across Amendia and an external system like Pega) to do, so Amendia can quietly check reality against that expectation. When something is late or never happens, a cohort flags it, warns you, and records who was accountable. It never pauses, forces, skips, or invents a step. Everything below is about describing an expectation — never an instruction.

1The vocabulary

A cohort is declared once, as a definition. Each real cross-system case that matches it becomes a running instance. Here are the pieces you'll fill in.

Correlation value

The one business key every system already shares for a case (e.g. the Pega case_id). It's the only handle — Amendia never shares its own ids outward, and the external system closes a cohort by this value alone. Must be unique per live case.

Segment (member)

A piece of the larger process that Amendia runs as a process pack. A cohort groups the segments Amendia is responsible for; the other systems' steps stay invisible to us.

Close message

The "the whole process is finished" signal the external system sends. You declare its shape (a JSON schema) plus where the correlation value and the final outcome sit inside it.

Expectation graph

A diagram of the segments you expect and the order you expect them in — the heart of this guide. Nodes are segments (plus a Start = "cohort opened"); edges mean "after this, expect that."

Expected vs conditional

Every segment is either expected (it should always run) or conditional (it only runs on some paths). This tells Amendia whether a no-show is a problem or simply a branch not taken.

SLA

A time promise on an edge or a segment: "this should happen within T." Amdia warns you as the deadline nears (at‑risk) and records it if missed (breached).

Owner (accountability)

Every SLA names who is on the hook — the external system (it hasn't invoked our segment yet) or Amendia (our segment is running slow). Breaches roll up by owner.

Clock

Each SLA is measured in wall-clock time (real elapsed) or business hours (against a configured calendar, so it doesn't tick overnight or on weekends).

2The expectation graph

Think of the graph as the sentence: "When the case starts, I expect segment A; after A hands back, I expect B; after B, either the release or the purge closeout; then the external system closes the case." You draw that as nodes and arrows. The graph is a directed acyclic graph (DAG) — arrows flow forward and never loop.

Two special nodes always exist: Start (the moment the cohort opens on the first segment) and Close (the external system's end-of-process message). Everything you expect lives between them.

3AND vs XOR branches

Whenever one node points to more than one next node, you must say which kind of split it is. This single choice is what lets Amendia tell "a segment is missing" apart from "a branch simply wasn't taken."

  • AND split — parallel work you expect to all happen. Every branch gets its own expectation and its own SLA; any branch that never arrives is a real breach.
  • XOR split — mutually exclusive options where exactly one path is taken. Mark those segments conditional. When one option arrives, Amendia voids the others — so an unchosen branch is never mistaken for a missing segment.

Not supported in v1: loops (a segment that repeats) and branches the external system decides in ways you can't enumerate up front. If you know the alternatives, model them as XOR; if you truly can't, leave that segment out of the graph and it simply runs standalone.

4SLAs — at-risk, breach, and owner

An SLA is always the same four-part promise. If you can fill in this sentence, you can declare it:

After [anchor event], expect [satisfying event] within [deadline + clock]; if not, it's on external / Amendia.

Two clocks per segment

Each segment has two moments you can attach an SLA to:

  • Arrival — the external system invoked the segment and Amendia started it. An arrival SLA answers "did the trigger show up in time?" → owner is almost always the external system.
  • Completion — the segment finished inside Amendia. A completion SLA answers "did our segment run fast enough?" → owner is Amendia.

That split is the whole point of attribution: the same case can breach because Pega was slow to invoke us, or because our own segment stalled on an approval — and the cohort tells you which.

At-risk before breached

You choose the at-risk lead (e.g. breach at 4 hours, at-risk at 3). At-risk exists so ops can chase the external system before the promise is blown — a breach is a fact you record, at-risk is a chance to prevent it.

Wall-clock or business hours

Pick per SLA. Wall-clock counts real elapsed time — use it for machine-to-machine steps that should happen fast regardless of the hour. Business hours counts only against a configured calendar (working hours + holidays) — use it for steps that wait on people, so an SLA doesn't "breach" overnight or across a weekend.

5Expected vs conditional — how a no-show is judged

This is the rule that keeps the cohort from crying wolf. When a segment you named never arrives, Amendia decides whether that's a breach or simply a path not taken, using the graph:

Node typeWhat happens if it never arrives
ExpectedA missing arrival past the deadline is always a breach (owner: external). Only an explicit failure or the whole cohort closing can excuse it.
ConditionalThe expectation is voided (no breach) the moment a resolving event proves the branch wasn't taken — see below. If no resolving event comes and the deadline passes, it still breaches.

A resolving event for a conditional segment is any of:

  • A sibling on the same XOR split arrives — e.g. the purge closeout shows up, so the release closeout is voided. (This is exactly why XOR siblings must be declared together.)
  • The cohort closes — the external system's end-of-process message voids any still-pending expectation. This is the case you flagged for a conditional last segment: the close proves it wasn't needed.

Why this needs the graph

"Some other segment arrived, so this one was skipped" is only safe to conclude when Amendia knows the topology. In a parallel (AND) world a sibling arriving means nothing about this segment; only an alternative-branch (XOR) arrival, or the close, proves a skip. That's why the expectation graph — not a flat list of segments — is what makes conditional segments trustworthy.

6Situations — which SLA catches what

Sections 1–5 give you the model. This section is the other direction: you arrive with a worry ("what if Pega never sends the second trigger?") and want to know which knob to turn. Start here, then §7 for the click-path.

◆ There are only three places a promise can attach

Every situation below is one of these. If you can decide which of the three you mean, the rest is filling in numbers.

  • An edge SLA — between two things: Start → segment, segment → segment, or segment → Close. This is the common one, and it is about waiting.
  • A node runtime SLA — inside one segment, from its arrival to its completion. This is about our own speed.
  • An end-to-end SLA — the whole case, cohort-open to close. One per graph.

⚠ The one most people forget

The segment → Close SLA. Every other promise fires because something was late; this one is the only thing that notices nothing happened at all. Without it a cohort whose external system quietly dropped the case stays open indefinitely and no one is told — the exact blind spot cohorts were built for. If you declare one SLA on a graph, declare this one.

Choosing the owner

The owner is what turns a cohort into an accountability ledger, so it is worth a moment's thought rather than a default. The rule is almost mechanical:

external — we were waiting

Anything measuring an arrival. They had the ball: the trigger never came, or came late.

amendia — we were slow

Anything measuring a completion. We had the ball: our segment stalled, usually on a human gate.

shared — the case as a whole

End-to-end. Nobody single-handedly blew it; the case simply took too long across both sides.

Nothing enforces this

Amendia does not check that arrivals are attributed externally. Attribute a completion to external and the ledger will quietly say something false. It trusts you.

Choosing the numbers

  • Set the deadline from what actually happens, not what you wish happened. Take the observed p95 for that hop and add margin. An SLA tuned to the hope rather than the behaviour breaches constantly, and a board that is always red is a board nobody reads.
  • At-risk around 70–75% of the deadline. Far enough out that chasing still helps; close enough that it isn't crying wolf. It must satisfy 0 ≤ at-risk < deadline or registration is rejected.
  • Business hours whenever a human is in the loop. A wall-clock SLA on a step that waits on an approver will breach overnight and every weekend, and those breaches are indistinguishable from real ones.

When not to declare one

Not every edge needs an SLA, and there is a real cost to declaring one you don't mean. A breach is permanent. If the work arrives after the deadline, the arrival is recorded as late but the breach still stands — that is deliberate (a promise that was missed was missed), but it means a too-tight SLA leaves a permanent red mark on a case that finished perfectly well.

The test: if this breached at 3am, would someone actually do something? If not, leave it off. You can always add it once you've watched the cohort for a while — which is the recommended order.

Mistakes worth avoiding

MistakeWhat you'll see
Owner attributed to the wrong side The board blames the external system for our slow approvals (or vice versa). Nothing errors — the ledger is simply wrong, which is worse than missing.
Wall-clock on a human step Breaches every night and weekend. Real breaches become invisible in the noise.
No segment → Close SLA A dropped case sits open forever and nothing surfaces it.
An SLA on every edge Alert fatigue — and in V1 breaches are surface-only (a badge and a live refresh; no email or push exists yet), so a noisy board is the only signal and it stops being read.
Expecting a breach to intervene It never will. A cohort has zero execution authority: a breach flags, warns and attributes. It does not abort, retry, skip, escalate, or nudge anyone. It is a record, not a control.
Marking an XOR branch expected Rejected at registration — and rightly: the branch not taken would breach every time.
Editing the graph while cases run Edits are forward-only (§9): running cohorts keep the graph they opened with. Your change affects the next case, not the one you're staring at.

7Declaring a cohort, step by step

  1. Name the case

    Give the cohort an id and display name, and declare the close message: paste its JSON schema and point to where the correlation value and the final outcome live inside it. This is how Amendia recognises "the process is over" and which case it belongs to.

  2. Add your segments

    Add each Amendia pack that's part of this process as a member, and map its correlation key — the field in that segment's trigger that carries the shared correlation value. A pack you don't add simply runs standalone.

  3. Draw the expectation graph

    Connect Start → your segments → Close with arrows in the order you expect them. At every point where one step leads to several, choose AND (all expected) or XOR (exactly one). Mark each segment expected or conditional.

  4. Attach SLAs

    On the edges/segments that matter, add a time promise: choose the anchor (arrival or completion of the prior step), the deadline and clock (wall or business), the at-risk lead, and the owner. Skip SLAs where you don't need a deadline — not every edge needs one.

  5. Review & register

    Check the graph reads like your real process, then register. If cases are already running under this cohort you'll see a forward-only warning — see §8.

8Worked example: the ACH exposure cohort

Pega orchestrates an ACH exposure-limit case and hands three segments to Amendia: Assess the exposure, Enforce the underwriter's decision, and Closeout — which is either a release or a purge, never both. The graph in §2 is this process. Here's how it's declared.

StepTypeSLA (anchor → satisfy, deadline, clock)Owner
Start → A · Assessexpected cohort opens → Assess arrives, ≤ 2h, wall-clockexternal
A → B · Enforceexpected Assess handback → Enforce arrives, ≤ 4h, businessexternal
B · Enforce runtimeexpected Enforce starts → completes, ≤ 30m, wall-clockAmendia
B → XOR C · Closeout (release | purge)conditional Enforce handback → one closeout arrives, ≤ 1h, wallexternal
C → Close— whole case ≤ 1 business day, end-to-endshared

Now watch how the same model attributes three very different bad days:

  • Pega never sends the Enforce trigger. The A→B arrival SLA goes amber at 3h, then breaches at 4 business hours — recorded against the external system. The case is stuck waiting on them, and you have the evidence.
  • Our Enforce segment stalls on an approval. The Enforce runtime SLA breaches at 30m — against Amendia. Different owner, same cohort.
  • The purge closeout runs (release doesn't). No breach — the purge arriving is a resolving event that voids the release branch. Had neither arrived and the case closed, both would be voided by the close.

9Rules, limits & gotchas

⚠ Edits are forward-only (for now)

Changing a cohort's graph or SLAs affects cases that open after the change. Cases already running keep the expectations they started with — Amendia will not retro-apply new deadlines to a case in flight. You'll see a warning when live instances exist. (Version-pinning may come later; today it's forward-only.)

  • Expectation, never execution. Nothing you declare here makes Amendia run, pause, skip, or force a segment. The graph only tells Amendia what to watch for. If the real external process diverges from your graph, the breaches you see are honestly measuring that divergence.
  • Only owners can declare or edit a cohort definition (the process-owner role). If you can't see the editing controls, you're signed in without that role.
  • One correlation value per live case. The correlation value is the sole handle and must be unique across running cohorts; reusing one would collide two cases.
  • Model known alternatives as XOR; if you genuinely can't enumerate a branch up front, leave that segment out of the graph rather than marking it expected (an expected no-show always breaches).
  • Business-hours SLAs need a calendar. Make sure working hours/holidays are configured, or a business-hours SLA can't be measured correctly.
  • No loops in v1. A segment that can repeat isn't expressible yet; model the single expected pass.

10Author's checklist

Correlation value chosen — one shared business key, unique per live case, and mapped on every segment.
Close message schema pasted, with the correlation and outcome paths pointed at the right fields.
Every Amendia segment added as a member with its correlation key.
Graph drawn Start → segments → Close; every fan-out marked AND or XOR.
Each segment marked expected or conditional (XOR options are conditional).
SLAs added where deadlines matter — anchor, deadline, clock (wall/business), at-risk lead, and owner set.
Owners assigned so breaches attribute to external vs Amendia correctly.
Read the graph back as a plain sentence — does it match the real cross-system process?
